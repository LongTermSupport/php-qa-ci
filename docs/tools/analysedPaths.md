# Analysed Paths

**Identifier**: `phpqaci.analysedPaths`

An always-on check that every directory holding PHP is either analysed or declared unanalysed
with a reason, so no PHP escapes the pipeline without someone having decided that it should.

## What it is about

PHPStan, Rector, PHP-CS-Fixer, the strict-types, lint and OPcache lanes read the **checked
paths**: `src/` and `tests/` by default, plus whatever `withCheckedPaths()` adds. PHP anywhere else
is never shown to any of them, and a rule cannot report a file it never visits. Nothing says so:
the run is green, and every rule appears to hold.

The case that prompted the check: a Symfony project's `config/services.php` carried
`$_ENV['X'] ?? ''`, the exact construction an enabled PHPStan rule forbids. The rule was on and
correct; it had simply never seen `config/`. No PHPStan rule can close that gap, because the
defect is the file not being analysed at all. This lane closes it from the other side: it lists
the project's PHP and accounts for every file.

## What counts

The lane lists the project's files through git (`git ls-files --cached --others --exclude-standard`): everything tracked, plus new files not yet committed, minus what
`.gitignore` excludes. Of those, every `.php` file still on disk must be under one of:

- a **checked path**: analysed;
- an **ignored path** (`withIgnoredPaths()`): already a deliberate, written exclusion;
- a path **declared unanalysed** with `withUnanalysedPath()`;
- a **default exclusion**: `vendor/` (third-party code) and `var/` (runtime output).

Anything else is reported by directory, with its file count. A PHP file at the project root,
such as `rector.php`, is reported by its own name, because declaring the root would excuse the
whole project.

Only the `.php` extension counts, because that is what PHPStan picks up from a directory. An
extensionless script such as `bin/console` is not analysed even inside a checked directory, so
listing it here would claim a coverage the analysers do not provide.

Two kinds of declaration fail too. A declaration matching **no PHP file** is stale: it would
silently excuse PHP added at that path later. A declaration **inside a checked path** is false,
because that PHP is analysed regardless.

An **ignored path** naming a path where nothing exists fails as stale for the same reason: every
scanning lane would skip whatever is added there later. An ignored path that exists passes
whatever it holds, since ignored paths routinely hold fixtures that are not PHP.

## How it runs

- In the full pipeline, in the linting phase, after the infection.json source directories check.
- Standalone: `vendor/bin/qa -t analysedPaths`, alias `-t ap`.
- A run narrowed with `-p` skips it: `-p` replaces the checked paths for that run, so everything
  else would read as unanalysed.
- A project that is not a git work tree skips with a reason: there is no file list to account for.
- A passing run prints every declaration with its reason, so the exclusions stay visible in every
  log rather than only in `qaConfig/qa.php`.

## How to fix a failure

Each reported directory needs one decision in `qaConfig/qa.php`, and the failure prints both
forms with the path filled in.

**Analyse it** when it is code the project maintains: configuration written in PHP, migrations,
public front controllers, scripts. This is the default answer, since it is what the pipeline is
for, and it may surface findings the directory has been accumulating unseen:

```php
return static fn (QaConfigBuilder $qa): QaConfigBuilder => $qa
    ->withCheckedPaths('config', 'migrations');
```

**Declare it unanalysed** when analysing it would be wrong rather than inconvenient: generated
code, fixtures that are deliberately broken, templates whose symbols only exist once copied into
another project. The reason is a required argument of at least two words, not a comment, so it
cannot be left out; it is printed beside the path on every run:

```php
return static fn (QaConfigBuilder $qa): QaConfigBuilder => $qa
    ->withUnanalysedPath('config/reference', 'generated by bin/console config:dump; rewritten on every deploy');
```

Declare the narrowest path that is true: a single file rather than its directory where only the
file is the exception. A declaration is an exclusion from every rule the project runs, so it is an
owner's decision, reviewed like any other suppression.

For a **stale** declaration or ignored path, delete it. For a **contradicted** one, delete it as well; to stop a
tool reading part of a checked path, use `withIgnoredPaths()` or the tool's own exclude setting.

## Worked example

php-qa-ci's own [`qaConfig/qa.php`](../../qaConfig/qa.php) declares each of its PHP paths
outside `src/` and `tests/` with the reason it is not analysed: the shipped tool configs and
`qaConfig/` templates, whose classes live inside the tool PHARs; its own `qaConfig/`;
`bin/bootstrap.php`, which the dead-code lane analyses as an entry point; the example rules in a
skill; and the php-src reproducer kept with a completed plan.

## Implementation

- Lane: [`AnalysedPathsTool`](../../src/Pipeline/Lane/AnalysedPathsTool.php).
- Decision: [`AnalysedPathsAudit`](../../src/Pipeline/Lane/AnalysedPaths/AnalysedPathsAudit.php),
  which accounts for each file against the paths and returns the verdict.
- Configuration: `QaConfigBuilder::withUnanalysedPath()`.
