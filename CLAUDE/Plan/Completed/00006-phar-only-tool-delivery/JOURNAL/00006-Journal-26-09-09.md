## 23:48 · finding · T1.3 — the PHAR update path never updated anything

Owner asked to make sure `composer update` keeps the PHIVE tools current. Checked with scratch
phive.xml files against real releases; every step below is a reproduced result, not a reading:

- `phive install` (what `tool-install.bash update` ran after deleting the PHARs) honours the
  `installed=""` pin: an entry `version="^1.3" installed="1.3.2"` reinstalled 1.3.2 although
  1.4.0 exists. So `composer update` → post-update-cmd → `tool-install.bash update` reinstalled the
  same versions every time.
- `phive install <alias>` with a warm PHIVE home resolves against the local cache first, so a
  cached older release that satisfies the constraint wins; only a fresh home went remote.
- `phive update` accepts neither `--copy` nor `--trust-gpg-keys` (`Unknown option`), so the
  `update-deps.yml` step has always failed into its `|| warning` branch. Even with a valid
  invocation it needs a TTY to import an unknown key (`Needs tty to be able to confirm`) and
  refuses unsigned releases (`No matching release found for php-parallel-lint/...`).
- The workflow also carried its own key list, missing the arkitect, twig-cs-fixer and
  composer-normalize keys added since.

Route that works, proven in scratch for one signed and one unsigned entry and then on the real
phive.xml: strip `installed=` attributes, fresh temporary PHIVE home, `phive install --copy
--trust-gpg-keys <all> --force-accept-unsigned </dev/null`. Both scratch entries resolved to
their newest release; the real run re-resolved all eight tools and produced identical bytes
(`git status` clean on vendor-phar/ and phive.xml). `update-deps.yml` now calls
`scripts/tool-install.bash update`; the duplicated key list and gpg import step are gone.

phpcpd); on the current `src/` it did not fire. Fixture test green (2 tests). Registered in
`rules-default.neon`, documented in `docs/phpstan-rules/forbid-bin-dir-tool.md` and the index.
