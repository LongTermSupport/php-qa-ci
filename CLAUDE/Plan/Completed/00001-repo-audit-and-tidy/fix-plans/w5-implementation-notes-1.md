## M-011 — Tool registry (single source of truth)

### Design

New file `includes/generic/toolRegistry.inc.bash` is PURE DATA + PURE FUNCTIONS,
sourced early by `options.inc.bash` (before `functions.inc.bash`), and safe to
source standalone. Per canonical tool it declares:

| Field (assoc array) | Purpose |
|---|---|
| `QA_TOOL_NAMES` (ordered) | authoritative order → usage listing + phase order |
| `QA_TOOL_ALIASES[name]` | accepted `-t` input tokens (the old `case` arms) |
| `QA_TOOL_TARGET[name]` | `singleToolToRun` value on selection (default = name; only `uniterate`→`phpunit`) |
| `QA_TOOL_ONSELECT[name]` | side-effect assignment `VAR=VALUE` (only `uniterate`→`phpUnitIterativeMode=1`), applied via `printf -v` (no `eval`) |
| `QA_TOOL_PATHS[name]` | `yes`/`no` path-support, applied to name + all aliases |
| `QA_TOOL_PHASE[name]` | `codingStandards`/`linting`/`staticAnalysis`/`testing` |
| `QA_TOOL_GATE[name]` | `notQuick` (phpstan, phpunit) / `infection` (phpqaQuickTests + useInfection) |
| `QA_TOOL_BANNER[name]` | phase banner label |
| `QA_TOOL_USAGE[name]` | `DISPLAY::DESCRIPTION` for the generated `-h` list |

Everything derives from it:

- `options.inc.bash`
  - `-t` resolution: `qaResolveSingleTool` replaces the 22-arm `case`.
  - path gate: `qaBuildPathSupportArrays` fills `PATH_SUPPORTING_TOOLS` /
    `NON_PATH_SUPPORTING_TOOLS` (the old hand-written, drifted, falsely-"VERIFIED"
    arrays); `tool_supports_paths` and its error listing are otherwise unchanged.
  - usage text: generated by looping `QA_TOOL_USAGE`.
- phase runners: the four `all*Tools.inc.bash` collapse to a single
  `qaRunPhase <phase>` call. `qaRunPhase` iterates `qaToolsForPhase` in registry
  order and runs each via the unchanged `runToolGuarded`, honouring
  `qaToolGateAllows` (the phpqaQuickTests / useInfection gates).

### IFS hazard (important, load-bearing)

`bin/qa` runs with `IFS=$'\n\t'` — **space is not a delimiter**. The
space-separated alias lists would therefore not word-split under the ambient
IFS. Every registry function that splits an alias list sets `local IFS=$' \t\n'`
first. This was caught during standalone smoke-testing and is covered by the
resolution smoke (all 40 tokens resolve through the real `options.inc.bash`).

### Behaviour preservation (frozen by tests)

`tests/Small/Pipeline/ToolRegistryCharacterisationTest.php` is a golden master:
GOLDEN_ALIAS_MAP (40 tokens), GOLDEN_PATH_SUPPORT (53 tokens), GOLDEN_PHASE_ORDER.
Committed FIRST parsing the pre-refactor structures (options `case` + phase
files); then repointed at the registry with the golden values unchanged — the
SSoT moved, behaviour did not. `ToolFragmentLivenessTest` likewise now derives
the registered tool set from the registry (its old `singleToolToRun="…"` regex
no longer exists) and still asserts every tool resolves to a real fragment.

Irregularities deliberately PRESERVED (they are the contract): a canonical name
is a valid `-t` input only when it appears in its own alias list (e.g. `-t
phpstan` works, `-t psr4Validate` does not); `uniterate` resolves to `phpunit`
and is classified non-path even though `phpunit` is path-supporting.

## M-053 — bin/qa composer-proxy self-parse (fork/rename tolerance)

Confirmed the bug with a faithful mock: the old
`cd $binDir/$(grep -Po "[^']+php-qa-ci[^']+" $binDir/qa)` finds nothing on a
forked/renamed package, so `$(…)` is empty and `cd $binDir/` silently resolves
`qaDir` to `$binDir` itself (→ `$binDir/../includes` does not exist).

Fix: scan the proxy's single-quoted path fragments and pick the one that
actually resolves (relative to `$binDir`) to the real `qa` script — accepting a
fragment that names either the script's DIRECTORY or the `qa` FILE itself, and
excluding `$binDir` itself. Independent of the install-dir name; fails loudly
(exit 1) instead of silently picking the wrong dir. This branch only runs under
a real composer install (`COMPOSER_RUNTIME_BIN_DIR` set), so it is not exercised
by the local self-test path; it was verified with a mock harness covering:
dir-style proxy (php-qa-ci — resolves identically to before), a renamed fork
(now resolves; previously mis-resolved), a file-style proxy fragment, and a
broken proxy (now errors loudly). `set -e`/`set -u` are not yet active at this
point in `bin/qa`, so the loop is safe.

Note on the handoff (bash-refactor-1 §5 / consumer-scripts WP-S8): M-053 and the
`bin/*` stub walk-up (M-071) were slated to share one project-root helper. I did
NOT extract a shared helper, because (a) M-071 lives in files outside this
wave's ownership (see below) and the plan asks the helper's location be agreed
with WP-S8 before it lands, and (b) the walk-ups differ (M-053 resolves the
LIBRARY dir from a proxy; the stubs resolve the PROJECT ROOT). Recommend the
scripts wave extract the shared helper when WP-S8 is done and refactor M-053's
block onto it then; the logic is self-contained and easy to lift.

No automated test was added for M-053: the logic is embedded in `bin/qa`'s
bootstrap proxy branch, unreachable in-process without a composer-proxy fixture
and a `COMPOSER_RUNTIME_BIN_DIR` harness. Extracting it into a sourced,
unit-testable helper is exactly the WP-S8 shared-helper coordination above;
recommend the test land with that extraction. The mock verification is recorded
here in the interim.
