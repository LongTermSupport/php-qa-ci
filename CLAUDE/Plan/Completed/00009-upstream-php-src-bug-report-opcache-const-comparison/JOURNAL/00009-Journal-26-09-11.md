## 09:05 · finding · T2.1 — the filed report conflated two builds, and the owner caught it

Yesterday's last entry recorded a caption fix. It was not enough. The backtrace came
from the **remi/EL9** build `php-cli-8.5.10-1.module_php.8.5.el9.remi.x86_64` (00007's
dossier records exactly that), while the `php -v` block and the
`Operating System: Debian 12, x86_64` field are *this* container, where the
reproduction was minimised. Both 8.5.10, two different distro builds.

The OS field is not wrong. This container really is Debian 12 bookworm running
`php8.5-cli 8.5.10-1+0~20260828.25+debian12~1.gbpfea0b8`, and the Fedora 44 in `uname`
is the **host kernel**, which a container shares and which says nothing about the
image. The error is that a reader takes the backtrace and the `php -v` to be the same
binary. `Zend/zend_vm_execute.h` is generated, so `:14374` need not correspond in a
Debian build.

Re-verified the reproduction live on this Debian build rather than asserting it from
memory:

| run                             | result                   |
| ------------------------------- | ------------------------ |
| default mask `0x7FFEBFFF`       | exit 139, segfault       |
| DFA bit cleared `0x7FFEBFDF`    | exit 0 → `int(1)`        |
| OPcache off entirely            | exit 0 → `int(1)`        |

and the const-const `IS_NOT_IDENTICAL null array(...)` is present in this build's own
dump. So the defect is independently confirmed on two distro builds — stronger than
what the issue actually claims.

**Owner ruled: do not edit the issue.** A corrected body was drafted in
`untracked/scratch/` and never sent; the issue has not been modified since posting.

## 09:12 · finding · P3 — verified upstream inside a day, with a different root cause

Triage: `Bug`, `Category: Engine`, `Status: Verified`. No question was asked of us.

ndossche's verdict, which **contradicts the cause the report leads with**:

> This is since 8.5 because of the empty array optimization in the VM.
> Ideally SCCP optimizes the resulting code too, but that's not the root cause, it's
> the inconsistent noconstconst marker.

`ZEND_IS_IDENTICAL_EMPTY_ARRAY` and `ZEND_IS_NOT_IDENTICAL_EMPTY_ARRAY` were the only
handlers in their group declared without `NO_CONST_CONST`. The unfolded comparison we
built the report around is a missed optimisation, not the defect.

Two consequences worth keeping:

1. **8.4 is unaffected**, confirmed by a maintainer and by the fix PR's `PHP-8.5` base.
   `FIRST_AFFECTED = 8.5.0` was right, and 00007 Decision 5's bet — that upstream would
   answer the 8.4 question for free — paid out exactly as written. Not building two PHP
   branches to answer it was the correct call.
2. **The lane's premise survives a wrong theory.** It looks for the *observable* (a
   comparison opcode with two constant operands), not for the cause, so being wrong
   about *why* did not make it look for the wrong thing. That is the general lesson:
   detect the observable, theorise separately.

## 09:31 · decision · T3.5 — the episode is now standing policy

Owner instruction: never accept a PHP segfault; any segfault is halt → debug → file,
with this as the archetype, plus the container core-dump caveat.

Written as [CLAUDE/segfault-policy.md](../../../segfault-policy.md) and made binding
from `CLAUDE.md`. Four steps rather than three — halt, debug, file, **defend** — because
the defend step (a detector in the pipeline) is what 00007 actually delivered and what
protects consumers while upstream works; leaving it out would have made the policy
describe half of its own archetype.

Two things from this episode are written into it as warnings rather than as history,
because both will recur:

- **A green pipeline is not evidence nothing crashed.** Five segfaults happened inside
  Infection mutant runs and every run still exited 0, because Infection scores a
  non-zero exit as a killed mutant.
- **The first theory can be wrong and the report still lands**, provided the
  reproduction is precise and the account of what was measured is honest. That is
  exactly what happened here.

The policy is repo-wide, so it lives in `CLAUDE/`, not in this plan folder.
