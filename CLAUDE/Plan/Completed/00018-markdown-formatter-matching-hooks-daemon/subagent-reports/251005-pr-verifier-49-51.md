#### B3 (BLOCKING): `realpath()` on the ignored side breaks an ignored path that is a symlinked directory under the source dir (reproduced)

- **Location:** `configDefaults/generic/phparkitect-class-set.php:40-44` and `:51`.
- **Mechanism:**
  - Arkitect's `ClassSet::getIterator()` builds its Finder with `->followLinks()`. Finder yields
    files under a symlinked subdirectory under the link's own name, for example
    `<proj>/src/Linked/L.php`.
  - The fix now runs each ignored path through `realpath()`, so an ignored `<proj>/src/Linked`
    becomes the link target `<…>/ext`.
  - The prefix comparison at `:79` therefore never matches, and the classes under the ignored
    directory are checked again.
- **Reproduced** with `src/Linked -> ../ext` holding `ext/L.php`, canonical srcDir, ignored
  `<proj>/src/Linked`:
  - `2c59bd0`: `L.php` dropped.
  - `e808b66`: `L.php` **listed**.
- **This is new in `18dc2f6`.** The PR's own previous head handled this case. The commit
  message also claims the opposite: "(or a symlinked path) drops the ignored classes too".
- **The lanes now disagree.** Every other lane compares the literal `IgnoredPaths::$absolute`
  (`src/Pipeline/Config/IgnoredPaths.php:50-56`). For this input, arkitect is now the one lane
  that does not honour `withIgnoredPaths()`. That contradicts the Unreleased › Fixed entry.
- **Severity:**
  - The shape is uncommon: a symlinked directory inside `src/` that the project ignores, for
    example shared or vendored code linked in.
  - No released behaviour regresses, because `php8.5` never honoured ignored paths in this lane.
  - It is the same defect class as B1: ignored classes reach arkitect because the two sides of
    the comparison use different path forms. The lead asked specifically whether `realpath()`
    on a symlinked path introduces anything, and it does.
- **No test covers it.** `ArkitectCheckTest` has no symlink fixture.
- **Fix direction:**
  - Match a Finder pathname against both forms of each ignored path, the literal and the
    canonical one.
  - Or fold `.`/`..` lexically instead of calling `realpath()`, as
    `IgnoredPathsInfectionConfig::absolute()` already does. That leaves symlinks alone and
    matches the other lanes.
  - Red test first: a fixture with an ignored symlinked directory under `src/`.

#### B2: fixed (verified against the phar)

From `vendor-phar/infection.phar` (Infection 0.35.6):

- `ConfigurationFactory::create()` sets `$configDir = dirname($schema->pathname)`, the directory
  of the config file it was handed. It calls `$schema->phpUnit->withAbsolutePaths($configDir)`,
  and likewise for `phpStan` and `mago`.
- `Entry/PhpUnit::withAbsolutePaths()`: `$configDir === null ? $basePath : makeAbsolute(...)`.
  `makeAbsolute()` keeps an absolute path. `PhpStan` and `Mago` are identical.
- `SchemaConfigurationFactory` uses `$rawConfig->phpUnit ?? new stdClass()` (and the same for
  `phpStan` and `mago`), so an absent section defaults in the same way.
- `resources/schema.json` declares `phpUnit`, `phpStan` and `mago` as objects with a string
  `configDir`. So writing `{"configDir": "<abs>"}` into all three validates, and Infection then
  uses that directory as it is.
- `IgnoredPathsInfectionConfig.php:100-105` pins an absent `configDir` to the original config's
  directory, which is exactly the value Infection would have defaulted to.
- An explicitly present `configDir` is left to `absolutise()`. An empty string `""` folds to the
  config directory, which is also correct.
