## 15:44 · decision · joseph — P1 — the two in-flight changes were feature-branched, not shipped

The Owner needed `php8.5` released so client projects can start consuming it, and separately
raised two design corrections mid-flight. Rather than hold the release for them, the release
went out at `085f595` and the corrections went to
`feature/twig-decoupling-and-variadic-narrowing`.

Both were the Owner's call and both are right:

**"we simply should not be suggesting variadic for anything with optional params"** — the rule
already skipped a parameter followed by an optional one, on the "unpacking after named
arguments" fatal. It did not skip a parameter carrying its OWN default, on the reasoning that a
variadic is inherently optional so nothing is lost. That holds only for an empty default: PHP
has no syntax for `string ...$items = ['a']`, so converting `f(array $items = ['a'])` silently
drops it. The exclusion now starts at the parameter itself.

**"the twig lint is not coupled to Symfony, it's coupled to Twig"** — right, and the two twig
lanes are not the same case. `TwigLintTool` shells out to `bin/console lint:twig`, so it IS
Symfony-coupled and stays a platform lane. `TwigCsFixerTool` runs a standalone PHAR with no
framework involvement, so gating it on `symfony.lock` meant a Slim, Laravel or plain library
project using Twig got no Twig coding standards at all.

Two things fell out of that second one that the original review missed:

- The gate was only half the coupling. `twigDirectories` defaulted to `[]` off Symfony, so a
  generic Twig project would have skipped anyway even after the gate changed. `templates/` is
  now the default on every platform, which is safe because the lane drops directories that do
  not exist.
- The lane's own read-only guidance has been telling users to run `vendor/bin/qa -t twigcs`
  since it was written, and that alias did not exist — platform lanes are not `-t` selectable.
  Moving it into the shipped registry fixes a latent defect nobody had hit yet.

## 18:12 · decision · — — T2.1 — phases became values, and each phase owns its runner

The builder could not be "add a phase" while `PhaseEnum` was the phase type: an enum is closed, and
`Pipeline` iterated `PhaseEnum::cases()`. So the phase is now a `PhaseDto` (name, banner, runner
name, runner aliases, runner description), the registry holds an ordered phase list, and
`ToolDefinitionDto::$phase` is the phase NAME rather than the enum case. `PhaseEnum` stays as the
source of the shipped four; `PhaseEnum::Linting->value` is what a shipped definition names.

Two smaller calls that fell out of that:

- The four `all*` runner rows are no longer listed in `ToolRegistry::shipped()`; the registry
  derives one from each phase. A project phase cannot exist without a `-t` runner, and a runner
  cannot point at a phase that does not exist. The characterisation test still sees the same
  tokens, in the same order, because the runners are emitted first, in phase order.
- `withTool()` takes the definition AND the `ToolInterface`, and refuses a pair whose names
  differ. The locator is keyed by canonical name, so a mismatch would be a lane that resolves to
  the wrong implementation at run time; better to fail in `qa.php`.

`QaApplication` builds through `PipelineBuilder::defaults()->build()` already, so the wiring
that Task 2.3 adds to `qa.php` is a hand-off of the builder, not a new code path.
`ToolDefinitionDto` is still `@internal` (Task 2.2): the builder is usable from inside the
library today, not yet from a consumer without the promotion.

Battery: 826 small tests green, PHPStan clean; the full writable run is in flight.

## 18:52 · decision · — — T2.3 — pipeline.php beside qa.php, not inside it

The task text said "wire the builder into qaConfig/qa.php". That file's contract is one closure
taking and returning a `QaConfigBuilder`; the pipeline builder has to be applied BEFORE the
arguments are parsed (it decides what `-t` may name), while `qa.php` is applied after. Folding
both into one closure would mean either a second return value, or a `withPipeline()` on the
config builder that couples two builders answering different questions. A sibling file,
`qaConfig/pipeline.php` returning `static fn (PipelineBuilder): PipelineBuilder`, keeps both
contracts single-purpose and is loaded by `PipelineConfigLoader` (same shape as
`ProjectConfigLoader`). If the Owner prefers one file, the loader is the only seam to move.

`QaApplication` now resolves the project paths first, applies `pipeline.php`, and only then
parses `-t`. A failure inside `pipeline.php` prints as `ERROR:` with exit 1, before any usage.
The characterisation test now derives its goldens from `PipelineBuilder::defaults()`, so it
freezes what the run uses rather than the literal it starts from. A Large test drives a fixture
consumer with a `pipeline.php` through the real entrypoint: `-t sa`, `-t allSec`, and `-h`
listing both.

## 19:09 · action · — — T4.3 — ForbidAmbiguousArrayDocRule shipped in rules-optional, sweep done

`phpqaci.ambiguousArrayDoc` (`src/PHPStan/Rules/ForbidAmbiguousArrayDocRule.php`, registered in
`rules-optional.neon`, docs at `docs/phpstan-rules/forbid-ambiguous-array-doc.md`) flags `T[]`
and single-argument `array<T>` / `non-empty-array<T>` in every `@param`, `@return` and `@var`
tag, including the `@phpstan-` and `@psalm-` prefixed forms. One report per tag, on the tag's
own line. Fixtures under `tests/assets/PHPStan/AmbiguousArrayDoc/`; the rule test pins seven
reportable lines and zero on the clean fixture.

Two traps met while proving it: PHPStan visits a class method twice (the parser node and its own
`InClassMethodNode` wrapper carrying the same docblock), so `VirtualNode` is skipped; and the
rule's own class docblock holds the WRONG example, so `ClassLike` is skipped too, which is safe
because a class docblock has no `@param`/`@return`/`@var` of its own to check.

The sweep touched 10 files: the recon's five `T[]` parameters plus the `array<T>` half in
`LinksChecker`, `ForbidHttpPrefixedEnvVarsRule`, `BranchNamePolicyConfig`, `LockInfoDto`,
`Psr4Validator` and two tests. Every fix states the keys (`list<T>`, `array<K, V>` or
`array<array-key, T>`); none loosens a type.

`composerRequireChecker` did not know `PHPStan\Node\VirtualNode` (PHPStan is a PHAR here, so
its runtime symbols sit in the whitelist beside `InClassNode` and `FileNode`); added it there.

## 19:27 · finding · — — T4.1 — yamlLint freed from bin/console; twigLint is genuinely coupled

`symfony/yaml` ships `Resources/bin/yaml-lint`, a standalone runner for its `LintCommand` that
needs only `symfony/console` (the script checks for it and exits 1 otherwise). It accepts
`--parse-tags`, so the lane loses nothing. `twig/twig` ships no linter: `lint:twig` is a
`symfony/twig-bundle` command that compiles templates against the application's own Twig
environment (extensions, functions, namespaced paths), and outside that environment a template
using an app extension fails to compile. So the audit's answer is one of each.

**Done**: `YamlLintTool` gates on `vendor/symfony/yaml/Resources/bin/yaml-lint` plus
`vendor/symfony/console` and runs the script directly; it moved from `platformLanes()` into the
shipped registry (`-t yamlLint`, alias `yaml`, after `markdownLinks`) and `yamlDirectories`
defaults to `config/` on every platform, mirroring `twigDirectories`. `platformLanes()` returns
only `twigLint` now. On this repository the lane skips (no nested symfony/yaml); on accounts-api
it will run through the script instead of `bin/console` once the lock moves.
