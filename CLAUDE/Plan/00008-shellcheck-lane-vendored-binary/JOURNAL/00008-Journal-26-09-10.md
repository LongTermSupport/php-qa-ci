## 14:55 · decision · T2.1 — the exec bit, which the PHARs never had to care about

Nearly shipped a lane that breaks for anyone installing from a Composer dist zip.
`ZipArchive::extractTo` does not restore permissions, so a dist-installed
`vendor-bin/shellcheck` arrives mode 0644. Every existing vendored artefact is a PHAR
handed to `php`, so this class of failure has never come up here.

`scripts/tool-install.bash` cannot cover it: its `post-install-cmd` fires for php-qa-ci's
own install, not a consumer's. So `ShellCheckBinary::ensureExecutable()` repairs the mode
at lane start and returns the reason when it cannot, which the lane prints.

## 15:05 · finding · P2 — PHPStan found 27, and three were real

The house rules did most of the work. Worth keeping:

## 15:45 · finding · T3.1 — correction: the required-checks risk is real after all

The 14:35 entry is wrong and this supersedes it. The owner's push of `php8.5` printed:

```
remote: Bypassed rule violations for refs/heads/php8.5:
remote: - Changes must be made through a pull request.
remote: - 2 of 2 required status checks are expected.
```

So something does require two status checks, and `ci.yml` had exactly two jobs —
`ShellCheck (severity=warning)` and `QA Pipeline`. Deleting the first leaves a required
context that never reports, which blocks every PR for anyone without bypass.

Why the earlier check missed it: `repos/LongTermSupport/php-qa-ci/rules/branches/php8.5`
returns only `deletion`, `non_fast_forward` and `pull_request`, and
`repos/.../rulesets?includes_parents=true` lists one repo ruleset. The status-check rule
must therefore live in an org-level ruleset, and `orgs/LongTermSupport/rulesets` needs the
`admin:org` scope this token does not have — it 404s. A negative from an endpoint that
cannot see the whole picture is not a negative, and I reported it as one.

The deletion stands; the rule change is owner-held and is now a box on Task 3.1.

## 15:55 · decision · T1.2 — the updater moved from Bash to PHP mid-build

Owner ruling, mid-task: real scripting should be PHP wherever possible. The ~90 lines of
Bash I had just written and proved were exactly what the ruling is about — a release
lookup, a JSON parse, an archive unpack and a five-way decision, none of it visible to a
test or to PHPStan. Untested Bash logic inside a tool that exists to catch untested logic.

Now: `InstallDecider` is a pure decision table with a test per branch (nine of them,
including the two the Bash never handled — an unpinned checkout, and a current pin whose
binary has gone missing, which the Bash would have reported as up to date). The I/O is
`ShellCheckInstaller`; the entry point is `bin/shellcheck-install`; `tool-install.bash`
keeps one `php` call and the token borrow.

Nothing is shelled out any more. Switching the asset from `.tar.xz` to `.tar.gz` is what
buys that: `PharData` reads gzip, so `curl` and `tar` both go. It costs 1.2 MB of download
on a maintainer-only path and removes two host dependencies.

The project's own guards did the review. `ComposerBinManifestTest` caught the new
executable missing from composer.json's `bin`; the catch-block rule rejected two silent
`catch (Throwable)`s, and turning them into printed causes means a rate limit no longer
looks like an empty release list. The ruling is recorded in `CLAUDE.md`, not just here,
since it governs the next script anyone writes.

## 17:55 · decision · T3.1 — owner ruling: fix the required check, do not remove it

I had framed the last open box as "the owner drops the ShellCheck context from the required-checks
list". The owner rejected that framing outright: **do not remove, fix.**

The reasoning holds up better than mine did. Removing the context trades a check that cannot report
for no check at all, on the one branch whose entire premise is that a green pipeline means a green
branch. I had reached for the cheap edit — make the rule match the world — instead of the correct
one, make the world satisfy the rule.

So `ci.yml` carries a `shellcheck` job again, named `ShellCheck (severity=warning)` to match the
required context exactly. What it runs is the difference: `bin/qa -t shellCheck`, the shipped lane
over the pinned `vendor-bin/shellcheck`, rather than an independently-installed ShellCheck. That
keeps the thing this plan actually existed to kill — three ShellCheck versions in play, one per
place it ran — while giving the branch rule something real to check. One mechanism, invoked twice.

The cost is one extra `composer install` per CI run for a job that duplicates a lane the QA job
already runs. That is the price of per-lane granularity on the branch rule, and it is worth it: a
red `ShellCheck (severity=warning)` names the failure on the PR without anyone reading the QA log.
