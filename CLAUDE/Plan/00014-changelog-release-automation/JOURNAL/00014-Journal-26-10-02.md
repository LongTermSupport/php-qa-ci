## 20:50 · decision · P2 — release pull request replaces bot commits

The owner asked for standard practice rather than a bespoke design, and for common sense on the open decisions. Standard practice for a curated changelog is the release pull request (release-please, changesets): a bot keeps a "Release X" pull request current, and the human merge is the release. It drops the write deploy key, its secret and the ruleset bypass, and nothing commits to `php8.5` except the owner. The off-the-shelf tools could not be used as they are: both derive the changelog from commit messages, while this changelog is hand-written and lane-enforced, and our major is the PHP line. So the pattern is kept and the existing `bin/changelog-release` drives it.

Finding that forced a code change: CI on the merged release pull request judges "since the last tag" with `## Unreleased` already empty, so the lane would have failed every release. The lane now counts a version section the base lacks as part of the record. `pending-tags` tags the commit that wrote the section (found with `git log -S`, which does not diff merges), not the merge commit.

Repository settings checked: Actions may open pull requests; no ruleset targets tags or requires checks; `allow_auto_merge` is false (the likely cause of the failing weekly `update-deps`, Task 3.5).

Decisions 2.3 to 2.6 settled: the 85.0.0 entries were moved into their own section; the consumer template always fetches full history; `add-tool-updates` writes versions from the pins; the `QaConfigDto` parameters default to off.
