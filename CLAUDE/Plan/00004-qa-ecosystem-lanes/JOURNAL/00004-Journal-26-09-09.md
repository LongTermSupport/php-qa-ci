## 09:25 · finding · — — DBF 3.1 record: repeated string literal within one class

**Class**: the same string literal written three or more times inside one class instead of
being defined once as a constant.
**Hazard**: the value has no single definition, so an edit to one occurrence leaves stale
siblings, and the reader cannot tell what the value means or whether two occurrences are
meant to be equal.

**Instance**: `'8.5.10'` written 20 times across `ComposerChecksToolTest`.

**Two independent search techniques, chosen before the rule existed**:

1. AST walk (same scratch script): per class, every `String_` that is not an attribute
   argument, an array key or an array-dimension index, of length three or more and not
   whitespace-only; reported at three or more occurrences. Found **197** (16 in `src/`,
   181 in `tests/`, `tests/assets` fixtures excluded).
2. Text search: per file, `grep -o "'[^']{3,}'" | sort | uniq -c` at three or more. Found
   200 lines over 89 files; the difference is the grep counting array keys and attribute
   arguments and seeing single-quoted strings only. Every AST instance appeared in the grep
   set; the grep found no excluded value that carries the hazard.

**Bounds** (each exclusion with its sentence):
- Array keys and array-dimension indexes: the repeated key is how an array shape is
  spelled, and PHPStan's array-shape typing reports a misspelt key where the shape is
  typed; a constant per key would obscure the shape.
- Attribute arguments: declarative metadata read by tooling, not values the class
  computes with.
- Fewer than three characters, or whitespace-only: too short to carry meaning that could
  drift.
- Fewer than three occurrences: two is as often coincidence as identity.
- A nested class-like is counted by its own InClassNode.

Next wider rule: the same literal repeated across classes in one namespace. Not built: a
cross-class constant is a design decision (which class owns it) and PHPStan analyses one
file at a time; the search found no cross-class repetition that a single-class rule leaves
unaddressed inside any one class.

**Runner check**: none; coding-standard class, the rule is the defence.

**Sweep decision**: all first-party source (`src/`, `tests/` excluding `tests/assets`
fixtures, `qaConfig/`); `vendor/` and `vendor-phar/` excluded as third-party.

## 11:45 · decision · — — Phase 3 recommendations, for the Owner

**Task 3.1, spaze/phpstan-disallowed-calls: adopt alongside, do not retire our rule.**

Retiring `ForbidDangerousFunctionsRule` was the attractive option and the evidence rules it out.
Of the ten functions we ban, eight are covered by two shipped bundles
(`disallowed-execution-calls.neon`, `disallowed-dangerous-calls.neon`), but `unserialize` and
`parse_str` appear in none of the five, so we would have to author and maintain those entries
ourselves. Worse, our rule exempts the two-argument `parse_str($s, $out)` and flags only the
one-argument form; spaze's allow-directives condition on parameter *values*, not on argument
*count*, so that exemption appears to be inexpressible — retiring would either over-report or
need a custom rule class, which is what we already have.

The decisive point is enforcement, not coverage. spaze bakes `allowIn`, `allowExceptIn`,
`allowInInstanceOf` and attribute-based exclusions into the same config layer as the ban. Our
`phpstanIgnoreJustification` lane audits `ignoreErrors` entries and nothing else, so a consumer
could add `allowIn: [tests/*]` to `eval()` and no lane would ask them to justify it. Adopting
spaze as the *only* defence would therefore open a silent narrowing route that the toolchain
cannot see — precisely the failure the justification lane exists to close.

So: keep `ForbidDangerousFunctionsRule` as the unconditional floor for its ten functions, and
adopt spaze's execution, dangerous and insecure bundles for the coverage we do not have at all
(weak hashing and randomness, unparametrized SQL calls, superglobals, the backtick operator).
Per the Owner's standing ruling, overlap between two engines is acceptable when kept in sync and
documented; a test will assert every function our rule names is still named by it, so the floor
cannot be removed by accident.

**Task 3.2, shipmonk/dead-code-detector: adopt opt-in, default off, and measure before enabling
it here.**

The stated precondition is met — the 10:55 probe confirmed the PHAR loads Composer-installed
extensions. The real question was the false-positive surface on a library, and the answer is
that there is exactly one knob: `@api` phpdoc on a class, interface or method marks it an
entrypoint. There is no "this is a library" switch. Without that annotation every public method
a consumer calls but `src/` does not would be reported dead, and `usageExcluders.tests.enabled`
— which the package recommends for all projects — makes it worse for us, because it stops our
own test suite from counting as usage.

That is not a reason to reject it; it is a reason not to switch it on blind. The 18 pipeline
types retagged `@api` earlier today are the start of the surface it would need. The task is
therefore: ship it behind `withDeadCodeDetection(bool)` defaulting to false, then run it over
this repository as a measurement and record the count of reports and how many are genuine before
deciding whether this repository turns it on. Its `--error-format removeDeadCode` autofix stays
out of the pipeline; on a library with an incomplete `@api` surface it deletes public API.

## 12:30 · finding · joseph — DBF 3.1 record: an array parameter that should be variadic

**Originating instance**, spotted by the Owner in review:

```php
/** @param list<string> $baseArgs */
private function runText(ToolContext $context, string $logDir, array $baseArgs): ToolResultDto
```

Owner's words: "use splat when you can to guarantee typed array".

**Class**: a method's last parameter is declared `array` and its element type exists only in a
`@param list<T>` docblock, where the signature could instead be `T ...$name`.

**Hazard**: the element type is a promise, not a check. Two things follow. The engine performs
no check at all at run time, so the guarantee holds only where PHPStan runs and can see the
call — which excludes a consumer project's `qaConfig/tools/*.php` override calling into this
library, the case php-qa-ci exists to serve. And the promise lives in a docblock, so it can
drift from the signature silently; a variadic cannot, because there is nothing to drift from.

**Honest limit on the hazard, recorded because it bounds how much this is worth**: at level max
PHPStan already rejects passing `array<mixed>` or `mixed` where `list<string>` is documented, so
for a *private* method whose callers are in the same file this buys little beyond deleting a
docblock. The real gain is at a boundary PHPStan does not analyse. The class is worth enforcing
anyway — consistency is the point, and the weaker cases cost nothing to convert — but this is a
convention, not a bug class, and the record should not pretend otherwise.

**Technique 1 — text search.** `grep -rn '@param list<\|@param array<' src/` returns 82
docblocks; pairing each with the following `function` line gives 13 signatures.

**Technique 2 — structural AST scan** (`untracked/scratch/variadic-scan.php`): every method whose
last parameter is declared `array`, read from the parse tree with no reference to any docblock.
It found **39**, including several the text search missed because the signature spans multiple
lines and the `@param` is not on the adjacent line — `SealingAttributeReader::factoryFor` and
`BranchNamePolicyDecision::decide` among them. The techniques are independent in the required
sense: technique 2 found instances technique 1 could not, and technique 2 needs no docblock to
exist at all.

Breakdown of the 39: 1 by-reference, 13 promoted constructor properties, 9 maps, **16
list-typed candidates**.

The 9 "no docblock" hits the scan first reported were a defect in the scan, not in the code:

3. **Maps, `array<K, V>` with a key type** (9). A variadic is always a list; a map has no

5. **Methods carrying `#[DataProvider]`** (1: `testPhaseOrderMatchesGolden`). PHPUnit passes

## 12:40 · finding · — — a cost of the variadic class, recorded before the sweep

`BranchNamePolicyDecision::decide(string $branch, array $exemptBranches, array $allowedPrefixes)`
takes **two** list parameters. Only the last can become variadic, so the conversion leaves two
conceptually identical parameters spelled differently — one `array $exemptBranches`, one
`string ...$allowedPrefixes`.

This is not a false report: the hazard is real for `$allowedPrefixes`, and converting it does
place that one under engine enforcement. But it is an honest cost of the class, and the rule
cannot avoid it, because "convert both" is not available — PHP allows one variadic and only in
final position. Recorded so the asymmetry in that signature reads as a known consequence rather
than an oversight.

No narrowing added for it. A narrowing exists to exclude code that does not carry the hazard,
and this code does.
