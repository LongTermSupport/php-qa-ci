## 15:41 · finding · T1.1 — the reproduction crashes, deterministically

00007's dossier could only show the *opcode*, and hedged: "whether that particular
file crashes or misbehaves depends on where the constant lands". Minimising against
the crash rather than the dump removed the hedge. Six lines, no php.ini, stock build:

```
$ cat m5.php
<?php
function f($x) {
    if (null !== $x || [] !== $x) { return 1; }
    return 2;
}
var_dump(f(null));

$ php -n -d opcache.enable_cli=1 -d opcache.file_update_protection=0 m5.php
Segmentation fault (core dumped)
```

What was stripped and survived: `declare(strict_types=1)`, the `?array` parameter
type, the `: string` return type, the string returns. What it needs:

- **Both branches must return a value.** Drop the returns and the branch is optimised
  away; no bad opcode, no crash.
- **The call must pass `null`.** `f([9])` takes the other branch and prints `int(1)`.
- **The file must be older than `opcache.file_update_protection` (2s default)**, or
  that setting must be `0`. Without this OPcache never optimises a just-written file
  — which is the same trap Task 1.2 of Plan 00007 hit in the lane itself. A first
  run of a freshly written reproducer prints `int(1)` and looks like a failed repro.
- **`-n` works because OPcache is built into this binary**, not loaded as a
  `zend_extension` (there is no `opcache.so` in `extension_dir`, and no
  `zend_extension` line in php.ini). That is what lets the report claim no php.ini
  and no extension beyond OPcache — and it retires the draft's weaker "Xdebug was
  not loaded in the crashing processes" phrasing, since `-n` unloads Xdebug outright.

Mask bisect re-run against the crash, not the dump: `0x7FFEBFFF` (default) segfaults,
`0x7FFEBFDF` (DFA cleared) and `0` both print `int(1)`. `-d opcache.jit=0
-d opcache.jit_buffer_size=0` changes nothing, so it is the plain VM.

## 16:02 · decision · T1.4 — no 3v4l link is possible, and no paste was needed to know

The previous entry treated this as an owner decision because testing it looked like it
required publishing the snippet. It does not. From the
[OPcache runtime configuration table](https://www.php.net/manual/en/opcache.configuration.php):

| setting                           | default      | changeable   |
| --------------------------------- | ------------ | ------------ |
| `opcache.enable_cli`              | `0`          | `INI_SYSTEM` |
| `opcache.optimization_level`      | `0x7FFEBFFF` | `INI_SYSTEM` |
| `opcache.file_update_protection`  | `2`          | `INI_ALL`    |

`INI_SYSTEM` means a script cannot set it — `ini_set()` will not work, and 3v4l offers
no per-run ini. So no 3v4l snippet can turn the optimizer on, whatever 3v4l's own php.ini
says. The report now carries one clause saying exactly that, and Task 1.4 is closed with
nothing published.
