# Plan 00020 — Journal 26-10-08

_Scaffolded by `mkplan.bash`; timestamps in this file are UTC._

> **Append-only activity log** for plan 00020. One file per day
> (`00020-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM, ONLY with
> `mkplan.bash --journal <plan-number> <category> <body-file>` (it stamps the
> real UTC time; a hand-written entry is denied); NEVER edit earlier entries
> (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` UTC 24h (the date is in the filename, also UTC); times increase
>   down the file. A file with no sentinel line above predates this system —
>   its times are local, zone unrecorded (legacy; never rewritten).
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff` | `correction`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - A `correction` corrects an earlier entry without touching it. Its `REF`
>   (`--ref`, required) names that entry: `HH:MM` in this file, or
>   `YY-MM-DD/HH:MM` in an earlier one. An entry a correction names in this
>   file no longer counts for time order, so a future-dated stamp can be
>   corrected at the honest time.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 11:46 · finding · T3.5 — Turbo halves PHPStan time here; binaries now 7 MB each

Turbo measured on this repository (PHPStan 2.3.0, PHP 8.5.11 NTS, linux-gnu-x86_64). The method: `turbo-ext/` from the `2.3.0` tag staged beside a copy of the phar, the lane's exact command, the result cache cleared before every run, three interleaved runs each way.

| Run | Off     | On      | Peak worker memory off → on |
| --- | ------- | ------- | --------------------------- |
| 1   | 19.61 s | 9.60 s  | 163.77 → 175.77 MB          |
| 2   | 20.06 s | 10.60 s | 165.77 → 173.77 MB          |
| 3   | 21.54 s | 7.96 s  | 167.77 → 171.77 MB          |

- **Speed:** wall time falls by more than half.
- **Memory:** worker peak rises about 6%, far below #18's +36%.
- **Output:** "No errors" both ways.
- **Process restart:** `diagnose` reports `Turbo extension: enabled (version 6351afb)`, loaded via a process restart. In 2.3.0 that restart covers the main process too, where #18 found workers only.

**Size has changed the trade-off.** Each PHP 8.5 binary at 2.3.0 is now about 7 MB, not the 0.85 MB #18 measured:

| Platform          | Size        |
| ----------------- | ----------- |
| linux-gnu-x86_64  | 7.28 MB     |
| linux-gnu-arm64   | 6.73 MB     |
| linux-musl-x86_64 | 7.28 MB     |
| linux-musl-arm64  | 6.57 MB     |
| macos-arm64       | 7.58 MB     |
| windows NTS / ZTS | 8.4 MB each |

The extension version (`.version`, a short SHA) changes with most PHPStan releases. Committing every non-Windows binary therefore adds about 35 MB to git history per PHPStan bump. How Turbo is delivered is for the Owner to decide:

- (a) commit every platform;
- (b) commit linux-gnu-x86_64 only;
- (c) fetch the host's binary at install time, pinned by checksum.

Phases 1 and 2 do not depend on it and go out in their own pull request first.

## 22:36 · action · —   — PR #83 merged; B1 and #82 part 2 fixed before it

PR #83 (Turbo, Tasks 3.1, 3.2, 3.3 and 3.5) merged as `f324011` after two fresh verifications.

Round 1 failed it on B1. The installer staged in the system temp directory, so the final
`rename()` crossed filesystems and copied into the existing `.so` inode. A PHPStan run that had the
old binary mapped crashed with SIGSEGV or SIGBUS while a reinstall ran. Under the segfault policy:
the cause was our installer, not PHP, so nothing was filed with php-src. The defence is red
`a7b6835` (a library on another filesystem, a hard link to the old binary must keep the old bytes),
and the fix `ad93c26` stages beside the binary with `TemporaryDirectory::besides()`.

The dead-code lane then reproduced #82 part 2. With Turbo, PHPStan forks its workers, and the fork
guard covers `phpstan.phar` only. `dead-code-detector.phar`, loaded through `--autoload-file`, was
read by every worker through one shared descriptor. On a cold result cache the run failed in 6 of
6 runs with Turbo and in 0 of 6 without it. The earlier 14 repro runs had a warm cache. Red
`81883eb`, fix `ea343e6` (`DetectorUnpacker`, into `var/qa/cache/dead-code-detector/`). After the
fix, 0 of 5 runs failed, and round 2 measured 0 of 6.

Round 2 passed. Its notes are filed as #84 (the same in-place rename in `ShellCheckInstaller`),
#85 (`DetectorUnpacker` recovery and pruning, and the lane check never seen failing) and #86 (no
detector for a second PHAR reaching a forking PHPStan). An upstream report to PHPStan about the
fork guard is drafted at `untracked/scratch/upstream-turbo-fork-guard-draft.md` and waits for the
Owner.

Task 2.3 is closed: the rule-listing and agent-summary tests pass on 2.3.0, and #52 was superseded
