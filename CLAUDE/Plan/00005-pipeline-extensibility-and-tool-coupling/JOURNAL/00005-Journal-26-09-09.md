## 15:44 · decision · joseph — P1 — the two in-flight changes were feature-branched, not shipped

The Owner needed `php8.5` released so client projects can start consuming it, and separately
raised two design corrections mid-flight. Rather than hold the release for them, the release
went out at `085f595` and the corrections went to
`feature/twig-decoupling-and-variadic-narrowing`.

Both were the Owner's call and both are right:

**"we simply should not be suggesting variadic for anything with optional params"** — the rule
already skipped a parameter followed by an optional one, on the "unpacking after named
arguments" fatal. It did not skip a parameter carrying its OWN default, on the reasoning that a
variadic is inherently optional so nothing is lost. That holds only for an empty default: PHP
has no syntax for `string ...$items = ['a']`, so converting `f(array $items = ['a'])` silently
drops it. The exclusion now starts at the parameter itself.

**"the twig lint is not coupled to Symfony, it's coupled to Twig"** — right, and the two twig
lanes are not the same case. `TwigLintTool` shells out to `bin/console lint:twig`, so it IS
Symfony-coupled and stays a platform lane. `TwigCsFixerTool` runs a standalone PHAR with no
framework involvement, so gating it on `symfony.lock` meant a Slim, Laravel or plain library
project using Twig got no Twig coding standards at all.

Two things fell out of that second one that the original review missed:

- The gate was only half the coupling. `twigDirectories` defaulted to `[]` off Symfony, so a
  generic Twig project would have skipped anyway even after the gate changed. `templates/` is
  now the default on every platform, which is safe because the lane drops directories that do
  not exist.
- The lane's own read-only guidance has been telling users to run `vendor/bin/qa -t twigcs`
  since it was written, and that alias did not exist — platform lanes are not `-t` selectable.
  Moving it into the shipped registry fixes a latent defect nobody had hit yet.

## 16:12 · finding · — — T3.1 — the dead-code-detector prerequisite does not apply to us

Correcting the 15:52 framing, which took the 00004 recon at face value. The recon warned that
dead-code-detector has no library mode and needs an `@api` sweep first, or it reports the whole
public surface as dead. True in general; checked against this repository rather than assumed,
and we already did that sweep for an unrelated reason.

`RequireApiOrInternalTagRule` forces every one of the 165 classes in `src/` to declare `@api` or
`@internal`. The 26 `@api` ones are exactly the consumer contract:

```
QaConfigBuilder  ToolInterface  ToolContext  ToolResultDto  PhpInvoker
ProcessRunnerInterface  ShippedTools  ConfigPathResolver  ReadOnlyGuidance
PlatformEnum  ToolOutcomeEnum  + the config and process DTOs
```

So there is no untagged public surface to be misreported, and **no case for excluding php-qa-ci
from its own dead-code run** — which matters, because a tool we exempt ourselves from is one we
cannot honestly recommend to a consumer.

Two smaller unknowns remain, neither blocking: whether class-level `@api` covers the class's
public methods or the tag is wanted per method, and that `usageExcluders.tests.enabled` has to
be on or a method reached only from tests counts as dead.

## 18:12 · decision · — — T2.1 — phases became values, and each phase owns its runner

The builder could not be "add a phase" while `PhaseEnum` was the phase type: an enum is closed, and
`Pipeline` iterated `PhaseEnum::cases()`. So the phase is now a `PhaseDto` (name, banner, runner
name, runner aliases, runner description), the registry holds an ordered phase list, and
`ToolDefinitionDto::$phase` is the phase NAME rather than the enum case. `PhaseEnum` stays as the
source of the shipped four; `PhaseEnum::Linting->value` is what a shipped definition names.

Two smaller calls that fell out of that:

- The four `all*` runner rows are no longer listed in `ToolRegistry::shipped()`; the registry
  derives one from each phase. A project phase cannot exist without a `-t` runner, and a runner
  cannot point at a phase that does not exist. The characterisation test still sees the same
  tokens, in the same order, because the runners are emitted first, in phase order.
- `withTool()` takes the definition AND the `ToolInterface`, and refuses a pair whose names
  differ. The locator is keyed by canonical name, so a mismatch would be a lane that resolves to
  the wrong implementation at run time; better to fail in `qa.php`.

`QaApplication` builds through `PipelineBuilder::defaults()->build()` already, so the wiring
that Task 2.3 adds to `qa.php` is a hand-off of the builder, not a new code path.
`ToolDefinitionDto` is still `@internal` (Task 2.2): the builder is usable from inside the
library today, not yet from a consumer without the promotion.
