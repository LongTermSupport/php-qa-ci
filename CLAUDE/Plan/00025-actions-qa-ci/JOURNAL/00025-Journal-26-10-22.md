# Plan 00025 — Journal 26-10-22

_Scaffolded by `mkplan.bash`; timestamps in this file are UTC._

> **Append-only activity log** for plan 00025. One file per day
> (`00025-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM, ONLY with
> `mkplan.bash --journal <plan-number> <category> <body-file>` (it stamps the
> real UTC time; a hand-written entry is denied); NEVER edit earlier entries
> (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` UTC 24h (the date is in the filename, also UTC); times increase
>   down the file. A file with no sentinel line above predates this system —
>   its times are local, zone unrecorded (legacy; never rewritten).
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff` | `correction`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - A `correction` corrects an earlier entry without touching it. Its `REF`
>   (`--ref`, required) names that entry: `HH:MM` in this file, or
>   `YY-MM-DD/HH:MM` in an earlier one. An entry a correction names in this
>   file no longer counts for time order, so a future-dated stamp can be
>   corrected at the honest time.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 18:47 · finding · — — Isolated lanes merged; a thing that outlives its starter, three times

The isolated-lanes slice is merged (actions-qa-ci pull request 13), after five verifier rounds.

`check` runs the actionlint lane on each file in a child process: this program started with a
hidden `lane` command, in its own process group, under a two-minute limit and a cap on what it
writes. A crash, a signal, any exit other than 0 or 3, an overrun of time or output is exit 4,
naming the lane and the file; a lane that fails on its own account is exit 3. The `rule` harness
still runs actionlint in its own process, and `dbf.json` says so.

What the verifiers found, each fixed test-first before the merge:

- a child that wrote `null` was accepted as clean;
- a process the lane process had started outlived it when it exited cleanly, because the group
  was ended only on a timeout;
- killing `actions-qa check` left the lane process running with no limit, since the limit lives
  in the parent (fixed with a parent-death signal from a locked operating system thread);
- the same kill left ShellCheck, the lane's own child, running (fixed by sending SIGTERM and
  having the lane process end its own process group);
- the README promised more than that: it now promises the end of what stays in the lane
  process's group.

The same class of defect, a thing that outlives the thing that started it, appeared three times,
at three depths. The test for each starts the real test binary as the program, kills it, and
asserts on the process that should be gone.

Separately, the php-qa-ci gate run for the plan-progress branch hung for 40 minutes in phpcpd
(`wait_for_partner`, 0% CPU) after phpcpd warned that a file under a scratch directory had
vanished while it scanned; the cause was not found, and a second run was started. If it happens
again it needs its own issue.
