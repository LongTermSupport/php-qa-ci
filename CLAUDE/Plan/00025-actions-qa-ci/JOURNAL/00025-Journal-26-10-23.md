# Plan 00025 — Journal 26-10-23

_Scaffolded by `mkplan.bash`; timestamps in this file are UTC._

> **Append-only activity log** for plan 00025. One file per day
> (`00025-Journal-YY-MM-DD.md`). `PLAN.md` tracks the plan (what/why,
> current state, tasks); this journal tracks what actually *happened* —
> findings, decisions, dead-ends, hand-off state — the linear lifecycle a plan
> document structurally cannot carry.
>
> **Entry grammar** — append new entries at the BOTTOM, ONLY with
> `mkplan.bash --journal <plan-number> <category> <body-file>` (it stamps the
> real UTC time; a hand-written entry is denied); NEVER edit earlier entries
> (corrections are new entries):
>
> ```
> ## HH:MM · category · REF   — optional short title
> ```
>
> - `HH:MM` UTC 24h (the date is in the filename, also UTC); times increase
>   down the file. A file with no sentinel line above predates this system —
>   its times are local, zone unrecorded (legacy; never rewritten).
> - `category` ∈ `action` | `finding` | `decision` | `thought` | `blocker` | `handoff` | `correction`
> - `REF` = optional task/phase ref (`T1.2`, `P1`) or `—`.
> - A `correction` corrects an earlier entry without touching it. Its `REF`
>   (`--ref`, required) names that entry: `HH:MM` in this file, or
>   `YY-MM-DD/HH:MM` in an earlier one. An entry a correction names in this
>   file no longer counts for time order, so a future-dated stamp can be
>   corrected at the honest time.
> - Bodies may embed fenced logs/diffs/snippets — no size limit — with a
>   one-line takeaway above the fence.
> - End a working session with a `handoff` entry so the next agent's entry
>   point is the last entry of the newest day-file.

## 01:31 · action · — — actions-qa-ci pull request 26 merged; pinact waits on a provenance route

Pull request 26 of actions-qa-ci (`6ca40f0`) is merged: the `install.sh` template, tested by running
it with `sh` against real bundles, and `actions-qa-dev install-script`, which fills a release's
version and checksums into it. Its first verifier found the script sound and 11 of 24 mutants alive;
the tests that kill them, and two edge cases (an empty `--prefix`, a prefix that starts with a dash),
went in before the second verifier passed it.

A verifier of that pull request overwrote the host's `/usr/bin/tar` through a symlink in its test
harness, so `tar` looped. The packaged binary was extracted from the cached Debian package and
checked against the md5 dpkg recorded; putting it back in `/usr/bin` is blocked by the project's
containment hook and left to the Owner, and the work meanwhile ran with the verified copy first on
`PATH`. Later verifier briefs forbid writing outside their own scratch directory.

The pinned pinact was the next slice and turned out not to be free. The v5.0.0 tarballs each have two
GitHub attestations, but `gh attestation verify` fails on this host with `verifying with issuer "sigstore.dev"` and gives no reason, and neither `cosign` nor `slsa-verifier` is installed. Pinning by
the release's `checksums.txt` alone is weaker than upstream offers, and installing a verifier adds a
tool, so the route is a provenance decision of the kind Task 1.5 makes for zizmor. The same decision
holds the pinact half of `fix` and `update-tools.yml` with its `tools bump`. The options are posted on
[#310](https://github.com/LongTermSupport/php-qa-ci/issues/310#issuecomment-6355208852) with three
other open questions: `selfHostedRunnerLabels`, `cel-go` and the corpus of public workflows.

Every slice the agent has found that needs no decision is now merged; the identifiers the design
names are all built except `versionPin`, which needs a release, and the zizmor ones of phase 4. What remains waits on the Owner (the provenance
route, the four decisions of #310, `cel-go`, the narrowing, the corpus, branch protection) or on the
first release, which the agent never cuts.
