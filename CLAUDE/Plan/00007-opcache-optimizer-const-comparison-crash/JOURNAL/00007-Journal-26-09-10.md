## 10:50 · finding · — — how the day got here

The owner reported "php is crashing quite a few times" with no location. Nothing in
the container showed it: no cores (the core pattern pipes to the host's
`systemd-coredump`), no fpm signals, no OOM, every pipeline log exit 0. `sudo dmesg`
reached the host kernel ring: five `php` segfaults at one instruction offset.
binutils symbolised it to `zval_undefined_cv`; the debuginfo packages pinned it to
`zend_execute.c:280`.

Time correlation put every crash inside a full-pipeline Infection phase, so the next
hours went into reproducing under Infection: a lifecycle-tracing prepend (Infection
refuses `auto_prepend_file`), strace over filtered runs, full runs, runs with a fake
DBGp listener, runs with `XDEBUG_MODE=off`, and two whole pipelines. All clean,
because they ran in the wrong consumer. Dead end recorded so nobody repeats it: the
consumer whose pipeline crashed was the other one.

## 12:45 · finding · T1.2 — dogfooding found two holes in my own lane

Writing a fixture and running the lane on it returned a PASS. Two real defects, not one:

1. `opcache.file_update_protection` (default 2s) means OPcache does not cache — and
   therefore never optimises or dumps — a file written moments ago. The fixers rewrite
   files earlier in the same run, so a just-fixed file was silently unchecked. Now
   forced to `0`.
2. More important, the lane could not tell "no defect found" from "nothing looked at".
   It now collects the files the dump actually covered and reports a CRASH naming any
   file that produced none, because a pass on an unchecked file is the one verdict this
   lane must never give.

Both are covered by tests. Without the fixture run, the lane would have shipped
reporting green on a codebase it had not read.

## 13:05 · decision · — — one `opcache` tool, not a tool per defect

The owner challenged the naming as tool bloat, and was right. A tool is a permanent
extension of the public API: a frozen `-t` token, a line of CLI help, a step in every
run, an identifier, a docs page. Paying that per finding would mean a new tool per
future OPcache defect, each recompiling everything.

Renamed to the inspection rather than the defect: `opcache` / `-t oc`,
`phpqaci.opcache`, `OpcacheTool`, `OpcacheDefects`, `Lane/Opcache/`,
`docs/tools/opcache.md`. The owner then asked for the judgement itself to be written
down, since making a new tool is legitimate and sometimes right — so
`CLAUDE/tool-boundaries.md` now states what a tool costs, the three-question test for
adding one, the group-by-inspection rule with the shipped lanes as worked examples, and
the `phpLint` vs `opcache` counter-example of two tools that share a mechanism and still
belong apart. Recorded as Technical Decision 3 in PLAN.md.

## 13:40 · finding · P1 — the default optimizer mask was wrong, caught by reading our own output

The `#[UsesClass]` additions cleared the 21 risky tests and the run reached Infection.
Reading the preflight lines in that run's log showed the advisory reporting the host mask
as `0x7FFEBFFF` while `OpcacheDefects::DEFAULT_LEVEL` said `0x7FFFBFFF`. Three probes with
`XDEBUG_MODE=off` settle it: PHP's default here, compiled-in and effective, is
`0x7FFEBFFF`. PHP ships passes `0x4000` **and** `0x10000` off; the constant had been
written as if the default were every bit set bar one.

Two real defects followed from it:

1. The lane compiled with `0x10000` on — an optimisation no production host runs — so its
   verdict was about bytecode nobody ever executes. Decision 2's whole point is to report
   what an unmitigated production host compiles, and the wrong constant broke exactly that.
2. The advisory recommended `0x7FFFBFDF`, derived from the invented default. Pasting that
   into a host with a deliberately reduced mask would have switched other passes back on.

Fixed: `DEFAULT_LEVEL = 0x7FFEBFFF`, and a new `recommendedFor(int $level)` clears the DFA
bit from the *host's own* mask, which is what the advisory now prints. Re-ran the bisect on
the dependency-free fixture against the real default:

| mask         | const-const `IS_NOT_IDENTICAL` |
| ------------ | ------------------------------ |
| `0x7FFEBFFF` | 1                              |
| `0x7FFEBFDF` | 0                              |
| `0x7FFFBFFF` | 1                              |
| `0`          | 0                              |

So the finding itself stands — the real default reproduces it and clearing `0x20` fixes
it; only the label was wrong. `0x10000` is not implicated either way. Corrected the mask
in the dossier table, the upstream report, `docs/tools/opcache.md` (which now also shows
how to derive the line from a non-default host mask), Decision 2 and Task 2.1. Three new
tests pin it: the default is not every-bit-set, the advice is host-relative, and the
advisory quotes the host's mask.

Lesson for the dossier's own credibility: the mask was a number I wrote from memory into a
constant and then repeated into four documents and an upstream bug report. Reading it off
the binary costs one command. The upstream report would have claimed a default PHP does
not ship.
