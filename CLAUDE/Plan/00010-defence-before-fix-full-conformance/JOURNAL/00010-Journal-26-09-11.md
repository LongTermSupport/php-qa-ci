## 16:41 · thought · P2/P3 — most of the clause table is one problem

Read end to end, the failures are not eleven unrelated defects. They are mostly one: **a
defence that cannot name itself.** Lanes print no identifier, PHPArkitect prints prose,
fifteen rules resolve to a summary and no page, the listing shows `identifier: null`, the
release guard accepts an index row, the agent block carries no rule lines. Identity and
resolution are the same requirement seen from different clauses — which is why the phases
run identity → resolution → enforcement rather than by clause number. A page for a defence
nothing resolves to is unreachable, and a tightened release guard would fail on gaps not
yet closed.

## 17:26 · decision · — — both sides are first party, and the separation is kept anyway

Owner pointed out what the plan's first draft did not account for: `Defence-Before-Fix`
and `LongTermSupport` are the same author. "Upstream" here means another repository, not
another party. Nothing stops us editing the specifications, the register entry, or our own
grade in it.

Two corrections followed.

**The README overclaimed.** It said the method is "specified independently of this tool",
which reads as third-party independence we do not have. Now: "specified **separately from
this tool** — same authorship, deliberately separate artefacts, versioned independently".
Public-facing text, so worth getting right before a reader discovers it themselves.

**The plan's Non-Goals were pointed at the wrong risk.** "Changing the specifications —
the route is a conversation upstream" assumed a gatekeeper. There isn't one, which makes
editing a clause to fit the tool the *easiest* available cheat rather than an impossible
one, so it is now named as exactly that. The real gate on a spec change is that repo's own
`ACCEPTANCE.md` process — fresh cold readers answering fixed questions about the text — and
that is a genuine cost, which is the point.

Recorded as Decision 4. The reasoning that survives being first-party: the register grades
PHPStan, Psalm, ESLint, Semgrep, CodeQL and dozens more, and its php-qa-ci entry says it
applies "the same scrutiny as every other entry". That sentence is the asset, and it is
worth more than a clean grade. The gaps it found are real and **we did not find them
ourselves** — our own declaration missed four of them. A register that flatters the
author's own tool would have missed them too.

Practical consequence for Task 6.2: re-auditing is a commit we can make, not a request we
file. Per-post Owner authorisation still applies, same as the php-src filing in 00009.

## 17:29 · finding · T2.2 — surfacing the route immediately found a broken one

`PipelineLaneDto` already carried an identifier; it was simply never rendered, and there
was no `docPath` at all. Adding both to the text listing and the JSON exposed one lane
that names itself on failure and resolves to nothing:

```
sensitiveParameterUsage (phpqaci.sensitiveParameterUsage)
```

The page exists. The index row links to it correctly. `RuleDocResolver`'s `LINK_PATTERN`
could not parse the link, because the link **text** contains a bracket:

```markdown
[`#[\SensitiveParameter]` is used somewhere in src/](../tools/sensitiveParameterUsage.md)
```

`[^\]]+` stops at the inner `]` and never reaches the `](` pair. Greedy matching is not
the fix — a row carries a bundle link as well as a doc link, and greedy would swallow
both — so the pattern now allows one level of nesting.

What makes this worth recording is that it is **silent by construction**. The row is
present and looks right; `bin/rule-doc phpqaci.sensitiveParameterUsage` still prints the
identifier, class, bundle and summary, and only omits the page body. Nothing anywhere
fails. Exactly the shape of defect the `known-gaps` reconciliation in T1.1 kept finding:
not a thing that is wrong, a thing that is quietly absent.

## 17:47 · finding · T3.1 — fourteen, not fifteen, and four had the wrong identifier

Enumerated from `bin/rules .` rather than the audit, per the task's own instruction. The
count is **fourteen**; the register's fifteen was a snapshot taken on `php8.4` at `e25aba4`.

Four of them could not be resolved by the identifier their class name suggested, because

| Class                                    | Identifier                                 |
| ---------------------------------------- | ------------------------------------------ |
| `ForbidAllowMockWithoutExpectationsRule`  | `phpqaci.forbiddenAttribute`               |
| `RequireRuleIdentifierConstantRule`       | `phpqaci.ruleIdentifierMustBeConstant`     |
| `ForbidMockingFinalClassRule`             | `phpqaci.mockFinalClass`                   |
| `RequireSensitiveParameterAttributeRule`  | `phpqaci.requireSensitiveParameterAttribute` |

`phpqaci.forbiddenAttribute` is the one worth a second look: it names a *category* rather
than the thing it forbids, so nothing about the identifier tells a reader which attribute
is meant, and it is the identifier a future rule about some other forbidden attribute would
naturally want. Not renamed here — it is a published identifier and a project may already
carry it in `ignoreErrors`, so changing it is an Owner decision, not a tidy-up.
