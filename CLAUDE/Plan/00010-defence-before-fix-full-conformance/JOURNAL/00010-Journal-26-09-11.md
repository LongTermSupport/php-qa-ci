## 16:34 · finding · T1.1 — our own gap record understates the gaps

The decisive finding, and the reason the plan starts where it does. Upstream publishes a
clause-by-clause audit of php-qa-ci, taken by *running* the commands in a checkout
(`bin/qa`, `bin/rules`, `bin/rule-doc`, `bin/phpstan-rule`) on branch `php8.4` at
`e25aba4`, 2026-09-08. Against our `composer.json` `known-gaps`:

| Clause                         | Upstream | In our known-gaps? |
| ------------------------------ | -------- | ------------------ |
| toolchain 4.1 (PHPArkitect)    | No       | yes                |
| toolchain 4.1 (PHPStan native) | No       | yes                |
| toolchain 4.1 (5 lanes, no id) | No       | **no**             |
| toolchain 4.2 (15 rules)       | Partial  | yes                |
| toolchain 4.3 (two baselines)  | Partial  | yes                |

| toolchain 8.1 (release guard)  | Partial  | yes                |
| detector 7.2 (ignore comments) | No       | **no**             |

Five omissions, none of them in our favour. Clause 9.2 makes the declaration "the claim and
the known-gap record", so an understated record is a defect in the one thing that clause
asks of us, independent of the gaps themselves. Hence Phase 1 — make the declaration honest
*before* making it shorter — and Task 1.2, a defence over the declaration so it cannot
drift again.

The five identifier-less lanes upstream names are `packageType`,
`phpstanIgnoreJustification`, `sensitiveParameterUsage`, `branchNamePolicy` and
`phpStrictTypes`. The audit predates `opcache`, `shellCheck` and `versionPins` on this
branch, so Task 2.1 re-audits rather than trusting that list.

The audit also reads `method 1.0.0` where `php8.5` declares `1.0.1`, and counts eight gaps
where we list six. Some of that is drift since the audit and some is the understatement
above; Task 1.1 separates the two by re-running, not by reasoning.

## 16:41 · thought · P2/P3 — most of the clause table is one problem

Read end to end, the failures are not eleven unrelated defects. They are mostly one: **a
defence that cannot name itself.** Lanes print no identifier, PHPArkitect prints prose,
fifteen rules resolve to a summary and no page, the listing shows `identifier: null`, the
release guard accepts an index row, the agent block carries no rule lines. Identity and
resolution are the same requirement seen from different clauses — which is why the phases
run identity → resolution → enforcement rather than by clause number. A page for a defence
nothing resolves to is unreachable, and a tightened release guard would fail on gaps not
yet closed.

## 16:52 · finding · — — DBF is already a Composer package, and already in consumers' vendor

Two answers to the owner's question about getting DBF into `vendor/`.

It needs no `type: package` hack: `Defence-Before-Fix/defence-before-fix.github.io`
**already ships a `composer.json`** declaring `longtermsupport/defence-before-fix`, type
`library`, CC-BY-4.0, docs-only, with an `archive.exclude` for the Jekyll machinery. It is
not on Packagist, so today it would need a `type: vcs` repository entry; publishing it
would make a plain `require` work.

And the specs are already reaching consumers as of this commit. php-qa-ci has no
`.gitattributes` and no `archive.exclude`, so **everything in the repo ships**, and it is
commonly installed from source as a full checkout — so `remote-docs/` lands at
`vendor/lts/php-qa-ci/remote-docs/` either way.

The remaining argument for a real `require` is not delivery, it is **version pinning**:
`extra.defence-before-fix` declares method `1.0.1` / toolchain `0.2.0` and nothing
currently checks those against the specification versions actually in use. A dependency
would make that machine-checkable — which is the same "declare the claim where it can be
checked" reasoning the declaration itself rests on. Left as an open question for the owner
rather than folded into the plan.
